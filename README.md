# 讯息窗

个人新闻摘要。手机优先的静态页面，没有构建步骤。推送到 `main` 后，GitHub Actions 把它发布到 GitHub Pages。

线上地址：<https://hene-gif.github.io/info-window/>

页面里的样式、脚本、数据和 manifest 都用相对路径，所以站点挂在 `/info-window/` 下也能打开。浅色和深色跟随系统。离线由 service worker、manifest 和图标负责。

## 页面

- 打开就是最新一期。`data/index.json` 的 `issues` 从新到旧，第一条就是本期。
- 页首只有两行。第一行是标志、期次名、研究、专栏、时间线、检索和收藏。点期次名会弹出列表：上面是专栏，下面是期次，可以换一期、看同一天的全部几期，或者进入全部往期。同一天可以有早、午、晚多期。
- 时间线只记影响够大的科技事件，不看新闻时间戳，也不是每天的摘要。发版本身不够，要写得出影响现象才进。点「时间线」打开一条从新到旧的竖线，点开一条看「影响」、来源，以及可选的相关条目。
- 专栏和期次分开。点「专栏」进入列表，点一篇打开全文。专栏里的「相关」会跳到对应条目所在的那一期，并展开那一条。
- 每一期固定两个栏目：「我关注的」和「国际重大影响」。页首第二行可以只看其中一栏。某一栏没有条目时，页面显示「这段时间没有」。
- 选中「我关注的」后，可以再筛子块。常见的是「AI 模型和产品动态」「人机恋和 AI 陪伴赛道」「语音交互和 AI 硬件玩具」「全球股市」。某一期里出现的其他子块也会列出来。
- 列表里每条只占标题和一行小字：编号 · 台北时间 · 来源。和本期同一天的时间只写钟点。点一下展开摘要、相关说明、来源链接和两个按钮，再点一下收起。
- 两个按钮复制的文字分别是 `聊聊 <条目 id>` 和 `收藏 <条目 id>`，中间一个空格。专栏同样如此，id 形如 `专栏-1`。
- 全文检索查全部期次、专栏和时间线的标题、摘要、相关说明、栏目、子块、编号、期次、来源和正文。
- 收藏页合并 `data/favorites.json` 和这台设备的 localStorage。条目和专栏都可以收藏。

## 加一期

一次提交，只改两个地方，可以直接推到 `main`：

1. 新建 `data/issues/<id>.json`
2. 把这一期插到 `data/index.json` 里 `issues` 数组的**最前面**（从新到旧）

不要改页面代码，也不要改 `sw.js`。发布前工作流会跑 `python3 scripts/check_data.py`。

期次 id 形如 `1014早`：两位月、两位日，再加时段。月日按台北日历，不足两位补零。常见时段是 `早`、`午`、`晚`。`1013试` 这种试刊把时段写成 `试`。哪一年写在 `date` 里，不写进 id。

条目 id 形如 `1014早-3`：期次 id、连字符、从 1 开始的序号。序号就是该条目在 `items` 里的位置。

栏目不是单独的数组。每条用 `section` 标明自己属于哪一栏。某一栏这次没有内容时，不要造占位条目；页面会自己显示「这段时间没有」。

## `data/index.json`

同一天有多期时，也按这个数组的顺序，把较新的放前面。

```json
{
  "version": 1,
  "issues": [
    {
      "id": "1014早",
      "date": "2026-10-14",
      "slot": "早",
      "title": "10月14日 · 早",
      "itemCount": 2
    }
  ]
}
```

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `version` | 数字 | 固定为 `1` |
| `issues` | 数组 | 从新到旧。同一天里也按这个数组的顺序，不另排 |
| `id` | 字符串 | `MMDD` + `slot`，例如 `1014早` |
| `date` | 字符串 | `YYYY-MM-DD`，台北的日历日，必须和 id 前四位一致 |
| `slot` | 字符串 | 和 id 里月日之后的部分一致 |
| `title` | 字符串 | 列表和窗口标题用的展示名 |
| `itemCount` | 整数 | 等于该期 `items` 的条数 |

## `data/issues/<id>.json`

文件名就是期次 id。`version`、`id`、`date`、`slot`、`title` 与目录里的那一条一致。`items` 按阅读顺序排列。下面是字段形状，不是要原样提交的新闻。仓库里现成的一期是 [`data/issues/1013试.json`](data/issues/1013试.json)。

```json
{
  "version": 1,
  "id": "1014早",
  "date": "2026-10-14",
  "slot": "早",
  "title": "10月14日 · 早",
  "items": [
    {
      "id": "1014早-1",
      "section": "我关注的",
      "block": "AI 模型和产品动态",
      "title": "标题",
      "time": "2026-10-14",
      "summary": "摘要。",
      "relevance": "",
      "sources": [
        {
          "label": "example.com",
          "url": "https://example.com/story"
        }
      ]
    },
    {
      "id": "1014早-2",
      "section": "国际重大影响",
      "title": "标题",
      "time": "2026-10-14T08:30:00+08:00",
      "summary": "摘要。",
      "relevance": "",
      "sources": []
    }
  ]
}
```

### 条目

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `id` | 字符串 | `<期次 id>-<序号>`，序号从 1 起，与数组位置一致 |
| `section` | 字符串 | 只能是 `我关注的` 或 `国际重大影响`，文字必须完全一致 |
| `block` | 字符串 | 仅 `我关注的` 要写，非空即可。常见子块见下面。`国际重大影响` 不要写这个字段，或者写 `null` |
| `title` | 字符串 | 标题 |
| `time` | 字符串 | 台北时间。只有日期时写 `YYYY-MM-DD`，不要配一个虚构的钟点。有钟点时写 `YYYY-MM-DDTHH:mm:ss+08:00` |
| `summary` | 字符串 | 摘要 |
| `relevance` | 字符串 | 相关说明。没有就写空字符串 `""` |
| `sources` | 数组 | 来源。每一项是 `{ "label": "短名称", "url": "https://..." }`。`url` 只接受 `http` 或 `https`。没有链接时用空数组 |

`我关注的` 常见子块，文字建议完全一致：

- `AI 模型和产品动态`
- `人机恋和 AI 陪伴赛道`
- `语音交互和 AI 硬件玩具`
- `全球股市`（美、日、韩、台、A 股 / 港股、欧洲，以及油、金、美债）

以后新加的子块直接写新名字即可。检查脚本只要这一栏的 `block` 非空就通过，页面会按出现过的子块分组显示。

只写日期的 `time` 按日历日显示，不会被当成 UTC 午夜再换算到另一天。没写时区的钟点会被当成台北时间。

## 加一篇专栏

一次提交，只改两个地方：

1. 新建 `data/columns/<id>.json`
2. 把这一篇插到 `data/columns/index.json` 里 `columns` 数组的**最前面**（从新到旧）

不要改页面代码，也不要改 `sw.js`。检查脚本会核对目录和正文，并确认 `related` 里的条目 id 真实存在。

专栏 id 形如 `专栏-1`：前缀固定是 `专栏-`，后面从 1 开始的序号。哪一天写在 `date` 里，不写进 id。

## `data/columns/index.json`

```json
{
  "version": 1,
  "columns": [
    {
      "id": "专栏-1",
      "date": "2026-10-14",
      "title": "标题",
      "summary": "导语。"
    }
  ]
}
```

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `version` | 数字 | 固定为 `1` |
| `columns` | 数组 | 从新到旧 |
| `id` | 字符串 | `专栏-` + 从 1 开始的序号 |
| `date` | 字符串 | `YYYY-MM-DD` |
| `title` | 字符串 | 标题 |
| `summary` | 字符串 | 列表和文首用的导语 |

## `data/columns/<id>.json`

文件名就是专栏 id。`version`、`id`、`date`、`title`、`summary` 与目录里的那一条一致。`body` 按阅读顺序排列。观点必须单独成节，`label` 写成 `观点`。仓库里现成的一篇是 [`data/columns/专栏-1.json`](data/columns/专栏-1.json)。

```json
{
  "version": 1,
  "id": "专栏-1",
  "title": "标题",
  "date": "2026-10-14",
  "summary": "导语。",
  "body": [
    {
      "type": "p",
      "text": "段落。"
    },
    {
      "type": "section",
      "label": "观点",
      "text": "这一节是作者的判断，不是消息本身。"
    }
  ],
  "related": ["1014晚-2"],
  "sources": [
    {
      "title": "文章标题",
      "outlet": "The Wall Street Journal",
      "url": "https://www.wsj.com/example",
      "date": "2026-09-28"
    }
  ]
}
```

### 正文块

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `type` | 字符串 | `p` 或 `section` |
| `text` | 字符串 | 段落。一节里若有多段，用空行（`\\n\\n`）隔开 |
| `label` | 字符串 | 仅 `section` 要写。意见节必须是 `观点`。其他节用来给后文加小标题 |

`related` 是条目 id 数组，例如 `1014晚-2`。页面会链到该条目所在的期次并展开它。必须能在现有期次里找到，不能重复。

`sources` 每一项是 `{ "title", "outlet", "url", "date" }`。`url` 只接受 `http` 或 `https`。`date` 为 `YYYY-MM-DD`。

## 加一条时间线

时间线只收影响够大的精选大事。日常摘要继续写进期次，不要整期搬过来。

入选看影响，不看新闻时间戳。不是「今天有个发布就记」。留下的每一条，影响都要够大；拿来对照的几条，也都要站得住，不能为了凑数收一条普通发布。

正文（目录和事件文件里的 `summary`，页面上标成「影响」）必须写出影响的现象：可观察的后果、格局变化、谁因此换了用法或定价，以及市场、开发者或闭源厂实际怎么动了。主语是「发生了什么影响」，不是「某日宣布了什么」。关键事实可以留作证据，不要写成发版通稿，也不要堆招股书数字。

写的时候对准现象本身。眼下这两条是：招股书把闭源前沿有多强摊开，并牵动市场对芯片、算力需求的信心；开源模型够便宜也够强，在闭源收紧时让人自己部署、把事做完。营收、亏损、单任务成本、下载量、进了某个工具，只能当证据或旁证，不能写成主影响。

发版本身不够，要写得出影响现象才进。研究预览、受邀测试，还看不出谁换了用法或定价、也看不出格局变了，就不要进。Google DeepMind Genie 4 就是这种：目前只是研究预览，尚未看到足以改变格局的影响，不要因为它刚发布了就新建一条。

一次提交，只改两个地方：

1. 新建 `data/timeline/<id>.json`
2. 把这一条插到 `data/timeline/index.json` 里 `events` 数组的**最前面**（从新到旧）

不要改页面代码，也不要改 `sw.js`。检查脚本会核对目录和正文。`related` 如果写了，里面的条目 id 必须真实存在。

事件 id 只用小写英文、数字和连字符，例如 `2026-10-26-anthropic-s1`。文件名就是这个 id。写进目录之后就不要改，否则旧链接会断。

## `data/timeline/index.json`

同一天有多条时，也按这个数组的顺序，把较新的放前面。

```json
{
  "version": 1,
  "events": [
    {
      "id": "2026-10-26-anthropic-s1",
      "date": "2026-10-26",
      "title": "标题",
      "summary": "把闭源前沿有多强摊开，并牵动对芯片需求的信心。"
    }
  ]
}
```

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `version` | 数字 | 固定为 `1` |
| `events` | 数组 | 从新到旧。同一天里也按这个数组的顺序，不另排 |
| `id` | 字符串 | 小写英文、数字、连字符。和文件名一致 |
| `date` | 字符串 | `YYYY-MM-DD` |
| `title` | 字符串 | 卡片标题 |
| `summary` | 字符串 | 影响现象，不是发版通稿。和事件文件里的 `summary` 完全一致 |

## `data/timeline/<id>.json`

文件名就是事件 id。`version`、`id`、`date`、`title`、`summary` 与目录里的那一条一致。现成的两条是 [`data/timeline/2026-10-26-anthropic-s1.json`](data/timeline/2026-10-26-anthropic-s1.json) 和 [`data/timeline/2026-10-17-deepseek-v41-flash-1017.json`](data/timeline/2026-10-17-deepseek-v41-flash-1017.json)。

```json
{
  "version": 1,
  "id": "2026-10-26-anthropic-s1",
  "date": "2026-10-26",
  "title": "标题",
  "summary": "开源、够便宜、也够强，让被限额卡住的人自己部署、把事做完。",
  "related": ["1027早-2"],
  "sources": [
    {
      "label": "sec.gov",
      "url": "https://www.sec.gov/example",
      "date": "2026-10-26"
    }
  ]
}
```

| 字段 | 类型 | 约定 |
| --- | --- | --- |
| `related` | 字符串数组 | 可选。讯息窗里已有的条目 id，例如 `1027早-2`。没有就省略，或写 `[]`。不能重复，必须能在现有期次里找到 |
| `sources` | 数组 | 至少一条。每一项是 `{ "label", "url", "date" }`。`url` 只接受 `http` 或 `https`。`date` 为 `YYYY-MM-DD` |

页面上点开卡片，小标题是「影响」，下面就是这条 `summary`，然后是来源和相关条目。地址 `#/timeline` 是整条时间线；`#/timeline/<id>` 会直接展开那一条。

## `data/favorites.json`

跨设备共用的收藏清单。最初是空的：

```json
{
  "ids": []
}
```

`ids` 是条目 id 或专栏 id，例如 `1013试-1`、`专栏-1`。不要写期次 id。页面上的顺序不跟这个数组走：专栏按专栏目录从新到旧，条目按期次从新到旧、期内按原序号。同一个 id 只出现一次。

本机另外有一份收藏，存在 localStorage，键名是 `info-window:favorites`，值是 JSON 字符串数组。点「收藏 &lt;id&gt;」会把这句复制到剪贴板，并把该 id 写入这个键。收藏页取文件和本机的并集。文件里有的条目会标成「清单」，只在本机的标成「本机」。收藏页上的「移出本机」只改 localStorage，不改仓库。

## 离线

`sw.js` 让装到主屏幕上的应用在断网时也能打开，联网时总是拿到最新的页面和数据。

- 页面、样式、脚本、图标和 `data/` 里的 JSON 都先走网络，取到就顺手存一份。断网时才用存下的那份。
- 安装时预存页面文件、目录、收藏清单、专栏目录、时间线目录，以及目录里列出的每一期、每一篇专栏和每一条时间线。哪个文件取不到就跳过，不会卡住安装。
- 缓存名带版本号。发布时 `scripts/stamp_sw.py` 按 `data/` 以外的全部文件算出版本号，写进 `sw.js`。页面代码一改，版本号就变：已经装好的应用会换上新的 service worker，删掉本应用的旧缓存，然后自动重新载入一次。
- 只加一期、只改数据时，版本号不变，不会重载。新的一期照样从网络取到。
- 从后台切回应用时，会检查一次有没有新版本、有没有新的一期，有就重新载入。

新加一期不必改 `sw.js`，也不用手动改版本号。

## 部署

工作流在 `.github/workflows/pages.yml`。它在推送到 `main` 时运行，也可以手动触发。没有站点构建，只检查数据，给 `sw.js` 写上版本号，再把页面文件交给 GitHub Pages。

第一次发布前，到仓库的 **Settings → Pages → Build and deployment → Source**，选择 **GitHub Actions**。

Settings → Pages → Source: GitHub Actions.

选好之后，合并到 `main` 的推送会发布到 <https://hene-gif.github.io/info-window/>。
